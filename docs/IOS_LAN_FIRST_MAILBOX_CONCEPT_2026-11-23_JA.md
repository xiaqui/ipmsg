# iOSからIP Messengerへ手紙を届ける構想（LAN優先・非常駐）

- 作成日: 2026-11-23

- 対象: `xiaqui/ipmsg`（Android / Windows の既存実装を維持）
- 関連: `ANDROID_WEB_LAN_BRIDGE_CONCEPT_JA.md`、`IOS_FUTURE_PLAN_JA.md`、`MULTIPLATFORM_ROADMAP_JA.md`、`SHARED_PROTOCOL_SPEC_JA.md`
- 現在進行中の `TASK.md`（v0.5.1 Release確認・実機検収）を変更・中断しない。

## 目的と優先順位

iOSだけ既存のAndroid/Windows IP Messengerから分断されているため、iPhoneから送った「手紙」を既存アプリの受信箱・履歴・通知に自然に取り込む。最初は **iOS → IP Messenger導入済み端末の一方向本文送信で十分**。iOS専用ネイティブアプリの開発を必須にしない。Appleショートカット／共有シートや軽いWeb UIを入口の候補とする。

**通信経路・利用基盤の優先順位は次のとおり（ユーザー確定）。**

1. **同一LAN内で完結**：到達可能な受信端末が動作中なら直接送信。外部サービス不要。
2. **会社Forgejo**：LAN直接送信できない、または受信端末が停止中なら、利用可能な会社Forgejoを非同期の郵便受けとして検討。
3. **GitHub**：Forgejoを利用できない場合の代替保管・受け渡し先。
4. **その他のサービス**：上記で目的を満たせない場合だけ候補を比較（ntfy、Cloudflare Workers + D1等）。

この順番は**検討・採用優先度**であり、「障害時に自動で全サービスへ転送する」仕様を決定したものではない。会社Forgejoの社内ポリシー、iPhoneからの到達性、API・認証・保管可否を先に確認する。個人メッセージを許可なく会社インフラへ保存しない。社内接続先URL、トークン、本文、端末指紋をリポジトリやログに記載しない。

## 方式の比較と現実的な制約

| 優先 | 候補 | iPhone側 | 受信側 | 利点 | 制約・確認点 |
| --- | --- | --- | --- | --- | --- |
| 1 | 同一LAN Web/HTTP入口 | Safari/ショートカットから現在動作中のIP Messenger端末にPOST（QRや宛先URLなど） | Android/Windowsアプリが受領し通常の受信処理へ | 最少の外部依存・低遅延 | **通信を受ける端末がその時点で起動・到達可能であることが必須**。端末常時起動は求めない。停止中はローカル配達不可 |
| 2 | 会社Forgejo | 認証付きAPI投稿（Issue / 専用データ等は要比較） | Android/Windowsから取得・検証・重複排除 | 既存基盤、専用サーバー不要 | 会社の利用許可、LAN外からの接続、権限、保存期限、監査ログ、API能力を要検証 |
| 3 | GitHub | ショートカット等から非公開repoのIssue/APIへ投稿 | Android/Windowsから取得 | APIの導入容易、Actions不要で運用可能 | プライバシー・トークン管理・API制限・取得頻度。Issueはあくまで試作候補 |
| 4 | 他サービス | HTTP/API送信等 | ポーリング／Push等 | 専用キュー・通知を設計しやすい場合あり | 新規運用・費用・事業者依存・暗号化・保管ポリシー |

**クラウドに保存しただけでは、受信端末へ即座にプッシュされない。** 定期取得の遅延とOSのバックグラウンド制約がある。Android/Windowsでアプリ表示中または既存の常駐機能が有効なときに取得し、バックグラウンド定期取得の頻度・電池・制限は別途実機評価する。「常時起動不要」は「停止中にも即時通知」の意味ではない。

従来の `ANDROID_WEB_LAN_BRIDGE_CONCEPT_JA.md` はAndroid親機のWeb子機構想であり、**親機が存続する条件**を持つ。今回はこれをLAN経路の候補として再利用するが、**常時稼働する親機を新たに要求せず**、停止中は保管型経路で後から届ける設計とする。WindowsをLAN受信入口にできるかも検討する。

## 論理構成（候補）

```text
iPhone（共有シート／ショートカット／Safari）
  │
  ├─ [優先1] 同一LAN内の起動中Android/Windowsへ直接送信
  │                        │
  │                        └── 検証後、既存IP Messenger受信箱へ
  │
  └─ 直接配達できない場合（明示的選択または合意済みのfallback）
         ├─ [優先2] 会社Forgejo の郵便受け
         ├─ [優先3] GitHub の郵便受け
         └─ [優先4] その他
                        │
                Android / Windowsが後から取得
                        │
                 署名・認証・重複確認
                        │
                  既存受信箱・通知
```

LANで「端末がいない」ことの検知はタイムアウトだけでは確定できない。**到着ACKが確認できない場合は配達成功と表示しない**。LAN送信後の応答喪失やfallbackによる二重配達を防ぐため、経路をまたぐ同一messageIdで冪等処理する。複数端末へ届ける場合、端末ごとの受領状態を区別する。

## 最小メッセージ仕様の論点（未確定）

- クライアント生成のランダムな `messageId`、版、作成時刻、有効期限、送信者の論理ID、宛先（特定端末／全端末／自分宛て）、本文、経路識別、認証用データを想定する。スキーマと本文サイズは実装前に確定する。
- 表示名だけを送信者認証とみなさない。iPhoneショートカット内の資格情報・長寿命PATの露出、アクセス範囲、取り消し、端末紛失時を考慮する。会社Forgejo/GitHubの認証成功は**既存IP Messengerの相互指紋承認と同義ではない**。
- 受信箱への取り込み前に署名/認証・宛先・期限・サイズ・重複を検証。未承認のクラウド送信者をLANの承認済み端末へ偽装しない。既存LANメッセージとクラウド由来メッセージの識別を残す。
- プライベートrepo、TLSやAPI認証だけではE2EEではない。サーバー管理者やサービス側から本文を秘匿したい場合は**送信前暗号化と鍵配布**を設計する。社内保管の適法性・利用規則を先に確かめる。
- 過去分の取得境界、再取得、ACK、重複排除、期限切れ、削除・掃除、複数端末受領を明示する。保管先のIssueを即削除して他端末への未配達分を失わない。
- ファイル・画像や双方向返信は後続候補。初期は本文のみ。既存のLAN暗号化プロトコル、相互承認、ファイル転送、保留キューの互換性を壊さない。

## 段階的な調査・検証案（実装未承認）

1. **LAN優先の技術調査**：iOS Safari／ショートカットから、起動中のAndroidまたはWindowsの限定HTTP受信口へ安全にPOSTできるか試す。ローカルIPの変化、QR/URL、iOSローカルネットワーク権限、HTTP/HTTPS、認証、アプリ停止時、OS差を検証。常時稼働親機は置かない。
2. **会社Forgejo適合性調査**：社内の規定・許可、iPhoneからの到達性、最小権限API、Issue/ファイル/その他の書込みの適性、監査・保存ポリシーを確認。実データ・認証情報は用いずモックから始める。
3. **GitHub代替経路**：Forgejoが不適の場合に限定し、専用非公開repo、Issue API等の最小試験を実施。Actionsはメッセージ受渡しに必須としない。
4. **統合MVP**：iPhoneから本文1件送信→既存IP Messengerの1端末に一度だけ受信表示。停止後の再開、通信障害、再試行、取り込みACKと未配達を確認。
5. **拡張判断**：Windowsも同一の受領状態管理を追加し、必要なら自動fallback、通知高速化、共有シート、画像、返信を別タスク化する。

合格条件の例：LAN到達可能時はクラウドに本文を置かず直接配達。受信側停止中でも許可済み保管経路へ投函でき、後に一回だけ受信。失敗・未確認は成功と表示せず、認証されていない内容を通常の承認済みLAN便と偽らない。
