# 開発・検収の略号集

更新：2026-10-19

GitHubのIssue、PR、会話、引き継ぎ書で使う短縮表記を統一する。

| 表記 | 正式名称 | 意味・使い方 |
| --- | --- | --- |
| **M1, M2…** | Milestone | 開発の節目・到達目標。例：M4（Android版最終検収） |
| **F1, F2…** | Feature | 機能・追加仕様 |
| **B1, B2…** | Bug | 発見した不具合の管理番号 |
| **P0〜P3** | Priority | 修正優先度・深刻度。Problemの略ではない |
| **T1, T2…** | Test | テスト・検収項目。合否と実機条件を記録 |
| **#12, #15…** | GitHub Issue / Pull Request | GitHub上の通し番号。同じリポジトリではPRとIssueが番号を共有する |

## 運用ルール

- **PRもIssueも原則 `#番号` に統一**。曖昧なときだけ「PR #12」「Issue #15」と補う。GitHub上での自動リンクにも対応する。
- **M・F・B・Tはプロジェクト内の管理記号**であり、GitHubが自動発行する番号ではない。文脈が足りないときは `M4-T3`、`M4-B2` のように所属マイルストーンを明記する。
- **Pは優先度**であり、件数でも問題IDでもない。P0は致命的、P1は重大、P2は中程度、P3は軽微な改善候補。具体的な修正必須基準は各タスク・レビュー指示に従う。
- テストに合格したときは `M4-T3 合格（XZ1／Ace III、日付）` のように、結果と実機／条件を残す。未実施を合格扱いしない。
- `C`（Criterion＝合格基準）は必要時だけ補助的に使う。通常はTごとに合格条件を直接書き、C番号を増やさない。

## 記述例

- `M4-T1 合格：XZ1で緑色の●表示を確認。`
- `M4-T3 未検証：Wi-Fi OFF/ON後の再探索。`
- `M4-T4でB2を発見。P1として#16で修正。`
- `M5-F1：Windows ⇔ Androidの基本送受信。`

※上のB2・#16は表記説明用の**架空例**で、実際の登録済み不具合・Issueを意味しない。
