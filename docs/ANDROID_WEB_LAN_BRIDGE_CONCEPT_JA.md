# Android親機・Web子機による家庭内LAN連携構想

- 作成日: 2026-10-14
- ステータス: **構想・技術検証前**。実装済みとみなさない。
- 関連リポジトリ: `xiaqui/wolf-chess`（Nearby Games）、`xiaqui/ipmsg`（家庭内IP Messenger）
- 本ファイルは**両リポジトリに同一内容**を配置する共通設計メモ。実装時には各repoの現行コードと既存docsを改めて確認すること。

## 1. 発想と目的

AndroidネイティブアプリをiOS向けに一から作り直すのではなく、**家庭の同一Wi-Fiに接続したAndroid端末をLAN内の親機（ホスト兼Webサーバー）にして、iPhone等のブラウザから子機として参加**できるようにする。

起点は「Kotlin製Androidアプリの表示やスクロールがHTML/JavaScriptに似ている。Web化できないか」という着想。ただしKotlinコードやAndroidの画面が**そのままHTMLになるわけではない**。既存ゲームルールや状態遷移の再利用可能性を調査し、ブラウザ用UIと通信接続部は別途実装する。

最優先は**自宅内で簡単に使えること**。外部クラウド・Apple Developer登録・App Store申請に依存せず、Androidアプリは引き続き利用できる構成を目指す。

## 2. 構成案

```text
                    同一Wi-Fi / 家庭内LAN
                              |
                  Android親機（ホスト）
                  ├ Nearby Games / ipmsg
                  ├ 既存Android向け処理
                  ├ LANセッション管理
                  ├ HTTPサーバー（HTML/CSS/JS配信）
                  └ WebSocket（双方向イベント/状態同期）
                       /              \
             Androidアプリ         iPhone Safari
             （ネイティブ）         （Web子機）
                                         |
                                     iPad/PC等も可
```

- Android親機がプライベートLANでHTTP/WebSocketサーバーを起動し、参加用URLとQRコードを表示。
- iPhoneはカメラでQRコードを読み取り、Safariでアクセス。アプリのインストール不要。
- 親機はルーム、プレイヤーID、参加・再接続、試合またはメッセージの状態を管理する。
- Androidネイティブ参加者とWeb参加者に、**同じゲーム状態・権限・結果**を配信する。
- ローカルネットワークだけで完結する構成は可能。ただしルーターのクライアント分離、端末ファイアウォール、OSの省電力制限に左右される。
- 親機Androidの起動・存続は必須。親機が停止した場合の復旧方式は別途設計する。
- **ブラウザからAndroidの既存LAN自動探索（UDPブロードキャスト/mDNS等）をそのまま利用できるとは限らない。** MVPはQR/URL入力方式。ホスト検出の改善は後続検証とする。

## 3. 共通アーキテクチャの原則

### 3.1 共通化の対象

ゲームルール、合法手、勝敗判定、ターン管理、COM思考、秘匿情報の扱いを可能な限り単一の**権威あるゲームエンジン**に集約する。初期MVPはAndroidホストが正本を保持し、Web側はユーザー操作を送信して画面を更新する方式が低リスク。

既存KotlinコードがAndroid SDKに依存している場合、そのままKotlin/JSで流用はできない。まず純粋なロジックへの切り出しを検討。将来必要ならKotlin Multiplatform/Kotlin/JS、あるいはブラウザ向けJavaScript/TypeScriptへの限定移植を比較する。**最初から大規模な共通化改修はしない。**

### 3.2 Web画面

HTML/CSS/JavaScript（必要ならCanvas）でスマートフォン用UIを新規実装。絵文字主体の盤面・カード表現を活かすが、フォント・絵文字差異、タッチ領域、viewport、縦横画面、スクロール、Safariの描画を実機確認する。ネイティブUIの自動変換ではない。

### 3.3 通信プロトコル

- WebSocket経由で`join`、`state`、`action`、`ack`、`error`、`leave`、`resume`等のイベントをやり取りする。
- 全メッセージに`protocolVersion`、`roomId`、`clientId`、`seq`または`actionId`を持たせる設計を検討。重複操作・再送・順序逆転を防ぐ。
- **親機で入力検証し、状態遷移を確定する。** Web側の合法手判定だけを信用しない。
- 初回接続時に状態スナップショット、以後は差分イベントまたは更新済み状態を配信。再接続時は正本から再同期する。
- LAN専用でも他の同一Wi-Fi参加者やゲストを想定し、短寿命の招待トークン/参加承認を検討。URLの漏洩、なりすまし、他者の部屋への参加を無制限に許さない。
- 初期HTTP/WSの利用可否を実機で確認。PWA・安全なコンテキストが要求されるWeb機能、HTTPS/WSS、ローカル証明書の扱いを別途評価する。**LAN内HTTPだけで全PWA機能が使えるとは言わない。**

## 4. Nearby Games（wolf-chess）への適用

### 4.1 MVP

**TIC TAC TOE+でAndroid親機 × iPhone Safari子機の1対1対戦をまず成立**させる。対象は起動、ルーム参加、手番、配置/スライド、勝敗、切断・再参加まで。既存Android同士のLAN機能を壊さない。

成功後の候補:
1. CONNECT 4G（複数人の手番・支配列・連鎖表示）。
2. WOLF CHESS（秘密情報の端末別フィルタリング、初期配置、リプレイの扱い）。
3. ROACH POKER（参加人数、秘密の手札、宣言、確認、受け渡し、途中離脱）。

### 4.2 特に重要な要件

- 秘匿ゲームでは**各参加者に見せてよい情報だけを配信**。全状態をWeb側に送りCSSで隠す実装は禁止。
- Android親機自身がプレイヤーの場合も、ホスト権限で手札・正体を覗けないようUIとプロトコルを分離する。AIも隠し情報を参照しない。
- 操作応答、リアクション/チャット、勝敗カウント、再戦同意、切断復帰をAndroid既存仕様と揃える。
- リプレイ/決着画面は種目別の既存方針を尊重し、機械的に全種目へ導入しない。特にROACH POKERは一人がリプレイ中だと再戦が止まる問題に注意。
- 端末間の色やMAN/COM表記、ルーム発見・参加UXなど現行仕様に合わせる。
- iPhone Safariのバックグラウンド遷移・画面ロック時はソケット断が起こり得る。復帰時に再接続して正本から再同期。

## 5. IP Messenger（ipmsg）への適用

Android親機が家庭内メッセージの中継・Web入口も担当すれば、**iPhoneからSafariで家族に送信・受信**できる可能性がある。

- MVP: QR参加 → デバイス/宛先の一覧 → 個別送信 → 同報送信 → 自分宛て送信 → 受信表示。
- 後続: ファイルの送受信、送達/既読状態、画像・添付のサイズ制限、通知、履歴と再接続同期。
- **Androidの全画面強制表示やロック画面上での封書的表示をSafariにそのまま移植できない。** iOSは前面表示や通知に制約があり、Web版では画面内の封書UIなど代替案が必要。
- iOS Safariを閉じている間の**常時受信・即時強制表示は保証できない**。Web PushはOS・ホーム画面への追加・権限・HTTPS等の条件を伴い、LAN専用構成との整合性検証が必要。
- 既存ipmsgプロトコルやAndroid実装がどこまで進んでいるかは**コード確認前のため未確定**。この文書から実装済み機能を推定しない。
- Nearby Gamesへのお誘いリンクは、Androidではアプリ起動、Webではブラウザ対戦URLへ分岐できる設計を検討。

## 6. 運用上のリスクと実験項目

1. **Androidの常駐**: フォアグラウンドサービス、通知、電池最適化、Wi-Fiスリープ、Android 8〜14以降のOS差を検証。バックグラウンド維持は無条件に保証されない。
2. **ネットワーク到達性**: Android端末のLAN IP変動、端末間到達性、ゲストWi-Fi隔離、ポート競合を確認。URL表示/QR、接続失敗時の診断表示を用意。
3. **Safari制約**: ローカルHTTPページ、WebSocket、音声再生、画面ロック、再接続、PWAホーム画面追加、端末ごとのUI差を検証。
4. **安全性**: 外部公開しないようバインド先・ネットワークを限定。HTTPは平文であり「LANだから安全」とみなさない。ファイル転送はパストラバーサルや容量上限を考慮。
5. **複数アプリの親機競合**: Nearby Gamesとipmsgが別個にWebサーバーを持つか、共通入口/ポート・セッションを持つかは**MVP実証後**に判断。初期から両repoを密結合しない。
6. **サーバー停止**: Androidのプロセス停止でWeb端末がどう復帰するか、再起動後のセッション復元と状態永続化を設計。
7. **既存機能の維持**: LANのAndroid同士、LOCAL/AI、配布APKへの回帰テストを必須にする。

## 7. 段階的な実装案と検収条件

### Phase 0: 技術スパイク（最小実験）
Androidアプリ内でHTTP + WebSocketサーバーを起動し、同一Wi-FiのiPhone Safariへ簡単なHTMLを配信。iPhoneのボタン操作がAndroidに届き、Androidからの状態更新がiPhoneに反映されることを確認する。QR・再接続・Android 8下限端末・iOS実機を確認。

**合格条件**: クラウド不要、2端末双方向通信、切断復帰、Android既存アプリ操作が壊れない。

### Phase 1: TIC TAC TOE+ 対戦
サーバー正本、操作検証、盤面同期、勝敗、再戦、二重タップ耐性、Safari再接続を実装。

**合格条件**: Androidネイティブ対Safariで1試合完走し、再試合・切断復帰・連続対戦が安定。

### Phase 2: Nearby Games展開
CONNECT 4G → WOLF CHESS → ROACH POKER等へ順次展開。秘匿情報の検証を優先。Android版同士の動作も維持。

### Phase 3: ipmsgのWeb子機
Android側で共通化できるホスト構成を評価し、ブラウザ送受信を最小実装。常時通知・強制表示については**実現可能な範囲を先に実機確認**。

### Phase 4: UX統合
家庭内ランディングページ、ゲーム参加招待、相互リンク、必要ならPWA化・セッションの再入室UX改善。
